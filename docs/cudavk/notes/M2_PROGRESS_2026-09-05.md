# M2, first working piece: the chunk-split tile walk

Branch `redesign/runlevel`. `REDESIGN_PLAN_2026-09-05.md` stage M2, partial.

## What was built

The driver already had a tiled opaque path behind `CUDAVK_TILED_OPAQUE`
(`cp_opaque_tile_visibility`, `cp_renderer.c`): it bins an episode's triangles
into 32 px tiles with a count/scan/fill, then rasterises them. Its walk gave
**one block a whole tile** and iterated that tile's references **serially**,
thread 0 doing each `setup_triangle` with a `__syncthreads` between them.

That is dead end 24's one-block signature exactly, and it is the reason both
previous tiling attempts were refused.

`cp_opaque_tile_raster_split` replaces it with the inversion
`RENDERER2_M1_WALKBENCH.md` measured and probe 4 confirmed:

- one thread per **reference**, so every setup happens in parallel;
- the tile's 1,024 pixels resolved in shared memory by `atomicMin` on the
  driver's own packed visibility word;
- a tile list longer than `CP_RUN_CHUNK` (512) split into several blocks
  **at bin time** from counts the scan already produced -- no dynamic
  claiming (dead end 2), no persistent kernel;
- blocks merged into the global visibility buffer with `atomicMin`, which is
  order-independent, so splitting cannot change the result;
- the chunk grid is an upper bound so no host readback enters the episode;
  empty blocks return immediately (dead end 9).

Revert: `CUDAVK_NO_TILE_SPLIT=1`.

## Measured, favorite3, 3 alternating rounds, arms disjoint

| comparison | control | candidate | delta |
|---|---:|---:|---:|
| **A** serial tile walk -> split walk, whole | 28.7643 | **8.0168** | **-20.7475** |
| **A** the same, heavy band | 35.3816 | **9.5405** | **-25.8412** |
| **B** default renderer -> tiled + split, whole | 5.9568 | 8.0607 | **+2.1039** |
| **B** the same, heavy band | 7.2867 | 9.5645 | **+2.2778** |

**A is the fix working.** The split walk is 3.6x faster than the serial walk
it replaces, which is the largest single measured change this campaign has
produced. Dead end 24's diagnosis was right and its signature is now gone.

**B is why that is not yet a win.** The tiled path as a whole is still 2.1
ms/frame slower than the renderer it would replace, and the reason is
structural rather than a tuning problem: **the tiled path is additive.** It
keeps the per-segment count and fill launches, keeps per-segment shading, and
still *issues* the classic `stage1/2/3` chain for every segment behind a
device-side predicate as its overflow fallback. The device skips those
launches; the host still pays for them. So the tiled arm issues strictly more
work than the default arm and wins only the visibility pass.

## Second iteration: the walk's mapping, and a corrected probe 1

**The first split walk was 318 us per launch.** One thread owned a reference
and walked that triangle's pixels inside the tile serially, so a triangle
covering a 32x32 tile put 1,024 pixel tests in one lane. Probe 4 never saw
this: its pool is tile-local, so no triangle was ever large. A game frame is
full of them.

Replaced with the classic tile mapping -- `CP_WALK_BATCH` of 32 references set
up **in parallel** into shared memory, then every thread tests its own four
pixels against the whole batch. 318 -> 217 us. A further optimisation, testing
a 16 byte shared bounding box before pulling the 80 byte setup, was worth
0.03 ms and is kept only because it is free.

**Probe 1 was wrong and is corrected.** The census omitted
`cpvk_draws_episode_compatible()`, so it let runs span viewport, rasterizer,
depth, blend and sample-count changes that the renderer reads once per
episode. With those carried:

| | first census | corrected |
|---|---:|---:|
| opaque runs | 2,153 | **5,265** |
| draws per opaque run | 181.3 | **74.1** |
| share of triangles | 90.8% | 90.8% |

Runs are **2.4x shorter** than first reported. The premise survives -- 2,941
runs still hold 64-242 draws, about 1.4 per frame -- but the headline number
in `RUN_CENSUS_2026-09-05.md` was too good and is now fixed. Note the driver's
*actual* opaque episodes are 6.21 segments (~20 draws), so the available
extension is 3.7x, not the 9x the uncorrected census implied.

## Why the tiled path is still slower, with the arithmetic

Per frame, from the trace:

| | ms/frame | |
|---|---:|---|
| split walk, 3.2 launches x 217 us | 0.694 | added |
| tile count, 22.1 launches | 0.207 | added |
| tile fill, 22.1 launches | 0.360 | added |
| **total added** | **1.261** | |
| stage1/2/3 displaced (21% of batches) | -0.146 | removed |
| **net** | **+1.12 expected, +1.71 measured** | |

**The tiled path pays a whole frame's binning cost to accelerate 21% of the
frame.** Opaque episodes hold 18 of the 86 batches issued per frame, so the
walk replaces a fifth of the rasterisation while the bin pass runs over
everything the episode contains. That ratio, not the walk's speed, is what
makes it lose.

## What M2 still needs, and it is exactly the plan's remaining sections

The plan removes the per-segment structure that the tiled path retains:

- **3.2 geometry per VS identity** with per-draw layout rows. Blocked on the
  fact `map_geometry` established: the vertex layout is strictly launch-wide
  and `CP_VF_FIXED_SLOTS` unrolls on a compile-time element index, so per-draw
  layout is an ABI change on the kernels carrying 110 launches a frame. Dead
  end 14 is the failure mode, dead end 42's `.local` census the gate.
- **3.5 compaction and one shade launch per identity, writeback fused.**
  Probe 2 says 13-18 identities per opaque run. The mechanism exists --
  `cp_seg_range` + `cp_resolve_seg_range` already shade many segments in one
  launch on the blended path -- but the writeback and interpolation state is
  still launch-wide (`map_shade` §10) and needs a per-segment descriptor.
- **removing the classic chain**, not predicating it, once the walk is trusted.

Until those land, `CUDAVK_TILED_OPAQUE` stays off by default and the M2 gate
(>= 1.0 ms/frame on the heavy band) is **not met**. The honest reading after
three iterations: **-26.3 ms/frame inside the tiled path, +1.95 ms/frame
against the default renderer** (heavy band, arms disjoint, bit-identical
output throughout).

**The order of work that follows from the arithmetic above** is coverage
first, not kernel tuning. Making the walk twice as fast again saves 0.35
ms/frame and still loses. Extending opaque episodes from 6.21 segments to the
74-draw run the corrected census measures is worth roughly 4x the displaced
term, and that is the only change that can turn the sign.

## Why coverage cannot be extended cheaply -- measured

`cp_batch_flush_why` now counts, under `CUDAVK_RUN_CENSUS`, what ends an
opaque episode. Every cut comes through one reason:

| reason | cuts | segments held |
|---|---:|---:|
| the next draw cannot join | 6,005 | 6.22 |
| render scope end | 26 | 4.77 |

and that reason splits, of the 3,809 attributable at the decision site:

| | cuts | share |
|---|---:|---:|
| **episode-wide state changed** (viewport, rasterizer, depth, blend, samples) | **3,043** | **80%** |
| the draw is not batchable at all | 766 | 20% |
| no batch pending | 0 | — |

The remaining ~2,200 are episodes whose only segment is the batch being
flushed -- one-segment episodes, of which the driver closes 2,198 of 6,031.

**80% of the coverage gap is the workload changing state that the renderer
reads once for a whole episode.** It is not a driver artifact, no relaxation
of the batch key removes it, and the plan's depth-only relaxation addresses
only part of the remaining 20%.

## Verdict on M2 as chartered

The redesign's opaque arm rests on runs being long. The corrected census says
a run of episode-compatible draws averages 74; the driver already collects 20;
and the difference is **state the plan assumes is episode-wide and the
workload changes anyway**. Collecting it would mean carrying viewport,
rasterizer, depth and blend *per segment* through the bin, walk, compaction
and shade -- a per-segment descriptor on every one of those kernels. That is a
larger change than M2 was chartered as, and it is a different design from the
one the plan argues for.

So the honest state is:

- the split walk **works, is bit-identical, and is 3.6x the serial walk**;
- the tiled path is **+1.95 ms/frame against the default renderer**;
- closing that needs ~4x coverage;
- 80% of the missing coverage is workload state, not driver conservatism.

**It is not proven impossible. It is proven not achievable by the route this
plan charts**, and the next honest step is to price the per-segment-state
design before building it -- the same discipline that closed dead ends 40-43.
