# M2, first working piece: the chunk-split tile walk

Branch `redesign/runlevel`. `REDESIGN_PLAN_2026-09-05.md` stage M2, partial.

## What was built

The driver already had a tiled opaque path behind `CUDAVK_TILED_OPAQUE`
(`cp_opaque_tile_visibility`, `cp_renderer.c`): it bins an episode's triangles
into 32 px tiles with a count/scan/fill, then rasterises them. Its walk gave
**one block a whole tile** and iterated that tile's references **serially**,
thread 0 doing each `setup_triangle` with a `__syncthreads` between them.

That is dead end 24's one-block signature exactly, and it is the reason both
previous tiling attempts were refused.

`cp_opaque_tile_raster_split` replaces it with the inversion
`RENDERER2_M1_WALKBENCH.md` measured and probe 4 confirmed:

- one thread per **reference**, so every setup happens in parallel;
- the tile's 1,024 pixels resolved in shared memory by `atomicMin` on the
  driver's own packed visibility word;
- a tile list longer than `CP_RUN_CHUNK` (512) split into several blocks
  **at bin time** from counts the scan already produced -- no dynamic
  claiming (dead end 2), no persistent kernel;
- blocks merged into the global visibility buffer with `atomicMin`, which is
  order-independent, so splitting cannot change the result;
- the chunk grid is an upper bound so no host readback enters the episode;
  empty blocks return immediately (dead end 9).

Revert: `CUDAVK_NO_TILE_SPLIT=1`.

## Measured, favorite3, 3 alternating rounds, arms disjoint

| comparison | control | candidate | delta |
|---|---:|---:|---:|
| **A** serial tile walk -> split walk, whole | 28.7643 | **8.0168** | **-20.7475** |
| **A** the same, heavy band | 35.3816 | **9.5405** | **-25.8412** |
| **B** default renderer -> tiled + split, whole | 5.9568 | 8.0607 | **+2.1039** |
| **B** the same, heavy band | 7.2867 | 9.5645 | **+2.2778** |

**A is the fix working.** The split walk is 3.6x faster than the serial walk
it replaces, which is the largest single measured change this campaign has
produced. Dead end 24's diagnosis was right and its signature is now gone.

**B is why that is not yet a win.** The tiled path as a whole is still 2.1
ms/frame slower than the renderer it would replace, and the reason is
structural rather than a tuning problem: **the tiled path is additive.** It
keeps the per-segment count and fill launches, keeps per-segment shading, and
still *issues* the classic `stage1/2/3` chain for every segment behind a
device-side predicate as its overflow fallback. The device skips those
launches; the host still pays for them. So the tiled arm issues strictly more
work than the default arm and wins only the visibility pass.

## What M2 still needs, and it is exactly the plan's remaining sections

The plan removes the per-segment structure that the tiled path retains:

- **3.2 geometry per VS identity** with per-draw layout rows. Blocked on the
  fact `map_geometry` established: the vertex layout is strictly launch-wide
  and `CP_VF_FIXED_SLOTS` unrolls on a compile-time element index, so per-draw
  layout is an ABI change on the kernels carrying 110 launches a frame. Dead
  end 14 is the failure mode, dead end 42's `.local` census the gate.
- **3.5 compaction and one shade launch per identity, writeback fused.**
  Probe 2 says 13-18 identities per opaque run. The mechanism exists --
  `cp_seg_range` + `cp_resolve_seg_range` already shade many segments in one
  launch on the blended path -- but the writeback and interpolation state is
  still launch-wide (`map_shade` §10) and needs a per-segment descriptor.
- **removing the classic chain**, not predicating it, once the walk is trusted.

Until those land, `CUDAVK_TILED_OPAQUE` stays off by default and the M2 gate
(>= 1.0 ms/frame on the heavy band) is not met: the honest reading today is
**-25.8 ms/frame inside the tiled path and +2.3 ms/frame against the default
renderer.**
