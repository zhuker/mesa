# **Architectural Redesigns for Device-Autonomous Unbounded Software Rasterization in Cudapipe**

## **Introduction and Architectural Context**

The engineering of high-performance software rasterization pipelines on Graphics Processing Units (GPUs) represents a sophisticated intersection of explicit graphics API compliance and massively parallel compute architecture. Cudapipe, an experimental Vulkan software rasterizer, attempts to bridge the historical gap between traditional CPU-bound software rasterizers, such as Mesa's Lavapipe and llvmpipe, and the parallel compute capabilities of NVIDIA's Compute Unified Device Architecture (CUDA)1. By replacing the CPU rasterization backend with highly specialized custom CUDA kernels, Cudapipe accelerates the processing of graphics primitives. However, this hybrid approach introduces profound architectural challenges, particularly concerning memory management and host-device control flow synchronization during order-dependent transparency operations.  
In its current architectural iteration, Cudapipe processes transparency by aggregating consecutive, compatible blended draws into a unified construct termed an "episode." The transparency path mandates that all depth-passing fragments be counted and stored in a global fragment array. To strictly preserve the exact Vulkan submission-order blending, the pipeline executes a multi-stage process: a prefix scan generates per-pixel fragment ranges; the fragments are sorted by their submission-order primitive ID; the fragments are geometrically grouped into ![][image1] primitive quads to ensure derivative-correct fragment shading; generated CUDA fragment shaders process these quads; and finally, a composite kernel blends the resolved results into the global A-buffer2.  
Because GPU memory within traditional CUDA paradigms must be statically allocated prior to kernel execution, the global fragment and quad arrays inherently possess finite capacities. When the geometric density or depth complexity of an episode exceeds these predetermined capacities, the rasterization kernels trigger GPU-side overflow flags. Under the current paradigm, before framebuffer writeback, the host CPU must explicitly wait for the GPU to synchronize, read the performance counters and overflow flags, and execute a conditional branch. If no overflow is detected, the pipeline proceeds to shade and composite the complete A-buffer. If an overflow is flagged, the host abandons the incomplete arrays and rerenders the episode utilizing a heavily iterative, multipass depth-peeling fallback algorithm5.  
Although actual overflow events are statistically rare—occurring approximately 5.6 times per frame on average—the conservative requirement to synchronize the host CPU and device GPU before every shading pass imposes a severe latency penalty. The CPU spends several milliseconds per frame blocked on synchronization mechanisms solely to verify the spatial integrity of the fragment arrays7. The central architectural challenge is to eliminate this host-device synchronization bottleneck, enabling the CUDA rasterizer to handle unpredictable fragment and quad populations entirely autonomously on the device, while strictly preserving Vulkan's submission-order blending guarantees and ensuring that incomplete data is never partially committed to the framebuffer.

## **Diagnostics of the Synchronization and Blending Bottlenecks**

To formulate a robust redesign, the precise mechanisms that render the current synchronization model unsustainable must be deconstructed. In heterogeneous computing, the CPU and GPU operate asynchronously. When the host dispatches a kernel, the operation is enqueued in a stream, allowing the CPU to proceed with other tasks. However, when control flow depends on data generated by the GPU—such as the overflow flags in Cudapipe—the CPU must stall its execution pipeline until the GPU completes all preceding work in the stream and flushes the result over the PCIe bus to host memory.  
This synchronization shatters the asynchronous execution paradigm. The CPU-side cost of preparing, submitting, and synchronizing a GPU kernel involves argument marshaling, stream synchronization, command buffer appending, and doorbell writes, which routinely consume between 5 to 15 microseconds per individual launch9. When multiplied across numerous episodes within a single frame, this latency accumulates rapidly. Furthermore, devastating pipeline bubbles are introduced on the GPU side; while the CPU evaluates the overflow flag over the PCIe bus, the Streaming Multiprocessors (SMs) sit idle, starving the device of work and plummeting overall hardware utilization9.  
Vulkan's strict blending specifications drastically constrain the allowable solutions. The standard alpha blending equation, typically defined mathematically as ![][image2] via the VK\_BLEND\_OP\_ADD operation, is mathematically non-commutative12. If multiple transparent primitives overlap a single pixel, they must be shaded and blended in the exact chronological order they were submitted by the application15. This stringent requirement fundamentally invalidates purely order-independent transparency (OIT) approximations or atomic blending directly into the framebuffer without prior sorting. Therefore, the pipeline is locked into a collect-sort-shade-blend methodology. If the global arrays responsible for the "collect" phase overflow, the subsequent "sort" phase will lack complete geometric data, violating the submission-order guarantee and producing severe rendering artifacts. Consequently, any viable architectural redesign must either mathematically guarantee that memory never overflows or possess a programmatic mechanism to dynamically invoke the overflow fallback entirely within the GPU's execution domain.

## **Paradigm I: Autonomous Device-Side Control Flow**

The most direct approach to resolving the CPU synchronization bottleneck involves migrating the control flow logic from the host to the device. Modern CUDA architectures have introduced sophisticated mechanisms for defining data-dependent execution topologies that evaluate conditions directly on the Streaming Multiprocessors, effectively bypassing the host CPU. By encapsulating both the optimal A-buffer path and the depth-peeling fallback path within a single GPU-managed structure, Cudapipe can entirely eliminate the host synchronization penalty.

### **Topology A: CUDA Conditional Graph Nodes**

CUDA Graphs permit the definition of a Directed Acyclic Graph (DAG) of operations, including kernels, memory copies, and memsets, that are submitted to the GPU in a single API call, thereby drastically reducing CPU launch overhead10. Historically, CUDA Graphs were static constructs; their topology could not change based on runtime data. However, the introduction of conditional nodes in CUDA 12.4, and their substantial expansion in CUDA 12.8, enables dynamic, device-autonomous control flow entirely within the encapsulated graph16.  
A conditional node evaluates a condition variable—stored directly in device memory and accessed via a cudaGraphConditionalHandle—to dictate which execution subgraph to trigger16. The condition value is explicitly set by a preceding GPU kernel using the device-side cudaGraphSetConditional API19. For Cudapipe, the entire rasterization episode can be structured as a single CUDA Graph encompassing a Switch conditional node (cudaGraphCondTypeSwitch), or an IF/ELSE node (cudaGraphCondTypeIf with a size of 2\)18.  
The execution flow would proceed with the host instantiating the episode graph and dispatching it asynchronously. The initial nodes in the graph consist of the rasterization kernels that process the primitives and populate the fragment and quad arrays. As these kernels execute, they utilize atomic operations, such as atomicAdd, to track the current capacity of the global arrays21. A lightweight, single-thread evaluation kernel is scheduled immediately after the rasterization phase. This kernel inspects the atomic counters; if the counters remain within the allocated capacity, it invokes cudaGraphSetConditional(handle, 0). If an overflow is detected, indicating that the fragment or quad arrays have been exhausted, the kernel calls cudaGraphSetConditional(handle, 1\)8.  
The subsequent node in the CUDA Graph evaluates this handle. Subgraph 0 contains the optimal pipeline: the prefix scan, submission-order sorting, quad processing, fragment shading, and composite kernels. Subgraph 1 contains the GPU-ported depth-peeling fallback pipeline. Because the conditional handle evaluation and the resulting control flow divergence occur entirely on the device hardware scheduler (the GigaThread Engine), the CPU is entirely decoupled from the decision23. The host simply submits the graph and proceeds to the next episode, achieving maximal asynchronous overlap.  
This architecture satisfies all constraints of the research question. It handles the unpredictable fragment population natively on the device, prevents the commitment of incomplete A-buffer results by abandoning Subgraph 0 entirely upon overflow, and guarantees Vulkan submission-order correctness by routing to an exact depth-peeling fallback. The primary engineering prerequisite is that the slow depth-peeling fallback, currently executed by the CPU, must be fully ported to CUDA kernels so it can be encapsulated within Subgraph 1\. Furthermore, conditional node body graphs enforce strict context limitations, stipulating that all kernels within nested conditionals must belong to the exact same CUDA context, a requirement Cudapipe already naturally fulfills17.

### **Topology B: Device Graph Launch (DGL) and Tail Launching**

An alternative to conditional graph nodes is Device Graph Launch (DGL), which permits a running GPU kernel to instantiate and launch entirely new task graphs at runtime without host intervention7. While conditional nodes require the entire superset of possible operations (both the optimal and fallback paths) to be predefined in a static DAG, DGL allows for the programmatic generation of workloads based on real-time heuristics.  
In a DGL-driven Cudapipe architecture, the initial rasterization kernels execute normally. Upon completion, a specialized device-side scheduling kernel assesses the overflow state. If no overflow is detected, the scheduler utilizes the cudaGraphLaunch API combined with the cudaStreamGraphTailLaunch execution environment to dispatch the shading and compositing graph7. A tail launch ensures that the dynamically generated graph executes sequentially only after the parent graph—and all its generated fire-and-forget children—have fully completed, preserving strict memory visibility and execution ordering without host intervention7.  
If an overflow is detected, the scheduler kernel discards the partially filled arrays and tail-launches the iterative depth-peeling graph. DGL provides a distinct advantage over conditional nodes when the fallback path is highly variable or recursive7. Depth peeling requires multiple passes, the exact number of which strictly depends on the maximum depth complexity of the current view. A scheduling kernel using DGL can iteratively tail-launch itself, dispatching one peeling pass at a time until the geometry is fully resolved, effectively operating as a highly autonomous device-side state machine7. This dynamic self-relaunching capability circumvents the need to pre-allocate an excessively deep static graph designed solely for worst-case depth complexity scenarios.

| Feature Comparison | CUDA Conditional Graphs | Device Graph Launch (DGL) |
| :---- | :---- | :---- |
| **Control Flow Topology** | Pre-compiled static Directed Acyclic Graph. | Dynamically dispatched subgraphs at runtime. |
| **Launch Overhead** | Near-zero (handled by GigaThread Engine). | Minimal, but incurs minor device-side launch latency. |
| **Fallback Handling** | Subgraph 1 executes the depth peeling pass. | Tail-launches iterative depth peeling kernels. |
| **Memory Portability** | Strict requirements; all nodes in the same context. | Highly flexible; permits dynamic memory allocation pre-launch. |
| **Recursion Support** | Requires bounded WHILE node loops. | Unbounded recursive execution via self-relaunching. |

## **Paradigm II: Unbounded Data Structures via Warp-Cooperative Paging**

While routing around memory overflow on the GPU mitigates the host synchronization penalty, the act of discarding rasterized data and falling back to a computationally expensive depth-peeling algorithm remains fundamentally inefficient. A more foundational architectural redesign involves modifying the underlying data structures to theoretically eliminate bounded capacity constraints, thereby rendering the concept of "overflow" practically obsolete.  
The current Cudapipe pipeline utilizes flat, globally allocated linear arrays for fragments and quads. When geometric density spikes, these contiguous blocks exhaust quickly. Transitioning to a dynamic, paged memory pool allows the rasterizer to draw memory elastically from the entirety of the GPU's available VRAM, bounded only by the physical limits of the hardware rather than an arbitrary pre-allocated buffer size defined by a single episode's conservative estimate.

### **Abandoning Flat Arrays for Lock-Free Slab Lists**

To achieve dynamic memory allocation during rasterization without destroying performance, Cudapipe can transition from flat arrays to lock-free, warp-cooperative linked lists, commonly referred to in high-performance GPU computing as slab lists24. Traditional per-pixel linked lists (PPLL), historically utilized for order-independent transparency, allocate memory per fragment. This requires a head pointer per pixel and appending individual nodes as fragments are generated25. However, single-fragment linked lists suffer from severe atomic contention and memory divergence, as adjacent threads within a warp may branch to wildly disparate memory locations, defeating the coalesced memory access patterns essential for high memory bandwidth utilization on GPUs26. Relying purely on atomicCAS (Compare-And-Swap) for single-node insertion causes exponential serialization penalties as depth complexity rises27.  
A slab list mitigates this by operating at the exact granularity of a hardware warp (typically 32 threads). A massive global memory pool is pre-allocated as an immense array of slabs, where each slab contains an array of elements equal to the warp size, plus a pointer to the next slab in the chain24. When a warp executes the rasterization kernel, the active threads identify depth-passing fragments. The threads cooperatively perform a ballot operation (utilizing intrinsics like \_\_match\_any\_sync or \_\_ballot\_sync19) to determine the total number of fragments generated by the warp. If the currently active slab has insufficient space, a single elected leader thread executes an atomicAdd against a global pool counter to claim a contiguous new slab from the heap24. The base address of this new slab is broadcast to all threads in the warp via register shuffle instructions, and the threads cooperatively write their fragments in unified, coalesced parallel transactions.  
This architecture provides an effectively infinite capacity for fragments and quads, bounded only by the multi-gigabyte VRAM capacity of modern GPU hardware. Because the memory is drawn dynamically on demand, the rigid episode capacities disappear. The prefix scan and sort phases must be adapted to traverse the slab list rather than a flat array. By sorting the dynamically allocated slabs based on submission-order primitive IDs, the pipeline seamlessly preserves Vulkan's precise blending mathematics. The necessity for the CPU to verify overflow flags is entirely eradicated because the structural limitation that caused overflows has been engineered out of the system.

### **Memory Granularity and Atomic Contention Modeling**

The success of the slab list architecture hinges on balancing allocation granularity with atomic contention. If the global pool counter is heavily contended by thousands of simultaneous warps across all SMs, the atomic serialization will stall the rasterization phase. To alleviate this, the global pool can be partitioned into multiple independent sub-pools distributed hierarchically across the Streaming Multiprocessors, or allocated using hardware-accelerated asynchronous allocators.  
Traversing linked lists during the sorting and grouping phases (Steps 4 and 5 of the Cudapipe transparency path) introduces pointer-chasing overhead, which can degrade L2 cache hit rates. The prefix scan, originally designed for highly optimized contiguous arrays, must be modified to perform a segmented scan across the distributed slabs. While this slightly decreases the raw instruction throughput of the sort phase compared to a perfectly flat array, the total elimination of the depth-peeling fallback and the associated CPU synchronization overhead results in a significantly higher net throughput for the overall episode. Furthermore, because fragments are grouped into ![][image1] primitive quads for derivative-correct fragment shading, the slab architecture ensures that related quads remain physically adjacent in memory, preserving texture sampling coherency during the shading phase2.

## **Paradigm III: Continuous Virtual Memory Expansion**

If refactoring the core data structures from flat arrays to linked slab lists requires too drastic an overhaul of the existing shader generation logic, Cudapipe can leverage low-level CUDA Virtual Memory Management (VMM) to dynamically resize the flat arrays without breaking their contiguous virtual addressing31. This allows the existing prefix scan and sorting algorithms to remain entirely untouched.

### **Decoupling Virtual Address Space from Physical Memory**

The traditional cudaMalloc API commits both virtual address space and physical memory simultaneously. If an array needs to grow to prevent an overflow, the application must allocate a new, larger buffer, copy the old data via cudaMemcpy, and free the original buffer—an unacceptably slow process that introduces immense latency31. CUDA VMM APIs decouple these operations entirely. The application can reserve a massive, contiguous block of virtual address space (e.g., hundreds of gigabytes) upfront using cuMemAddressReserve31. Because this operation only reserves virtual address space, it does not deplete actual physical VRAM33.  
As the rasterization kernels populate the fragment arrays, they monitor the physical capacity threshold using a device-side counter. When the fragment population approaches the boundary of the currently mapped physical memory, the system dynamically allocates new physical memory handles using cuMemCreate, maps them sequentially into the reserved virtual address space using cuMemMap, and enables access via cuMemSetAccess31. Because the newly mapped memory is appended directly to the end of the existing virtual range, the fragment and quad arrays remain perfectly contiguous in the eyes of the executing CUDA kernels. The prefix scan and sort algorithms require absolutely zero modification, as they simply operate over a larger virtual array.

### **Asynchronous Pager Threads and Execution Overlap**

A critical caveat to the VMM paradigm is that the memory mapping APIs (cuMemMap, cuMemSetAccess) are strictly host-side driver functions; they cannot be invoked directly from device code32. Consequently, triggering a memory expansion inherently requires CPU interaction, seemingly violating the objective to keep operations entirely on the device.  
However, this limitation can be expertly circumvented through aggressive execution overlap and asynchronous pager threads, an architectural pattern proven highly successful in demand-paging mechanisms for Large Language Model (LLM) inference engines (e.g., vAttention architectures)35. Rather than waiting for the GPU to completely overflow and halt execution, the rasterization kernel can set a "high-water mark" flag in mapped host-device memory (zero-copy memory) when the arrays reach 80% capacity. A dedicated, lightweight background CPU thread continuously polls this flag using a highly efficient spin-lock or the cudaStreamWaitValue32 mechanism.  
When the high-water mark is breached, the asynchronous CPU thread immediately issues the cuMemMap and cuMemSetAccess calls to expand the physical backing of the virtual array, while the GPU continues executing and filling the remaining 20% of its currently mapped capacity36. By the time the GPU reaches the absolute end of the previously allocated physical boundary, the Translation Lookaside Buffer (TLB) and page tables have already been updated by the CPU thread. This effectively hides the driver latency and allows the GPU to proceed uninterrupted into the newly mapped memory without a single blocking synchronization stall36.

| VMM Memory Granularity | Mapping Latency | TLB Thrashing Risk | Internal Fragmentation | Recommended Use Case |
| :---- | :---- | :---- | :---- | :---- |
| **4KB Pages** | Extremely Low | Severe (High overhead) | Negligible | Not recommended for high-bandwidth GPU processing. |
| **64KB \- 256KB Pages** | Low | Low to Moderate | Low | Highly optimized for dynamically growing arrays. |
| **2MB Huge Pages** | Moderate | None | Severe | Standard CUDA default; wastes physical memory on small overflows. |

To optimize this architecture, the physical memory allocation granularity must be carefully tuned. While standard CUDA APIs default to 2MB page sizes, which can cause severe internal fragmentation if an episode only overflows by a few kilobytes, modern systems programming research suggests tuning the VMM granularity to smaller pages (e.g., 64KB or 256KB) to balance TLB thrashing against memory bloat35. This architecture flawlessly preserves the contiguous array logic of the original Cudapipe pipeline, entirely eliminates the catastrophic depth-peeling fallback path, and maintains asynchronous GPU execution, provided the CPU pager thread can successfully race ahead of the GPU's memory consumption rate.

## **Paradigm IV: Tiled Sort-Middle Architecture**

The fundamental vulnerability of Cudapipe's current design is the reliance on a single, global A-buffer for the entire framebuffer. Modern hardware rasterizers, as well as highly optimized software rasterizers like CudaRaster and Nanite, systematically circumvent global bottlenecks by employing a tiled, sort-middle architecture3. By conceptually partitioning the Vulkan framebuffer into smaller, independent spatial tiles (e.g., ![][image3] or ![][image4] pixels), the unbounded global capacity problem is compartmentalized into bounded, highly localized problems.

### **Binning and Tile-Local Work Queues**

In a tiled redesign, the pipeline introduces a coarse binning stage strictly prior to fine rasterization38. Consecutive compatible draws within an episode are processed by a geometry kernel that determines which bounding tiles each primitive intersects. The primitive IDs and relevant vertex data are appended to tile-specific work queues.  
Instead of generating fragments into a massive global array, a grid of thread blocks is dispatched, where each thread block takes exclusive ownership of a specific tile. The thread block pulls primitives from its associated bin, rasterizes them, and performs the depth testing and fragment generation entirely in the SM's ultra-fast, low-latency shared memory38. Shared memory serves as a highly efficient local A-buffer. Because the geographic footprint of a tile is microscopically small compared to the full screen, the maximum theoretical depth complexity that can fit within a shared memory allocation is substantially higher relative to a global memory buffer.

### **On-Chip Shading, Quad Derivatives, and ROAA Emulation**

Within the tile, fragments are grouped into ![][image1] quads for proper derivative calculations, ensuring that texture mipmapping and anisotropic filtering function correctly2. Because all primitives within the tile's bin are inherently ordered by their submission ID, the threads can sort the generated fragments locally using highly efficient shared memory radix sorts38. Once the fragments are sorted, the thread block natively executes the generated CUDA fragment shaders, applies the VK\_BLEND\_OP\_ADD mathematics in strict submission order, and composites the final pixel colors directly into the global framebuffer12.  
If a specific tile exhibits pathological depth complexity and overflows its shared memory allocation, it does not trigger a global pipeline failure. Instead, only that specific thread block gracefully spills its excess fragments into a localized global memory buffer, or executes a multi-pass resolve internally without interrupting the execution of the other independent tiles.  
This architecture elegantly mirrors the Rasterization Order Attachment Access (ROAA) paradigm defined in the Vulkan specification (VK\_EXT\_rasterization\_order\_attachment\_access), which allows fragments at overlapping locations to be read and written safely without global pipeline barriers, provided they are localized and ordered correctly43. By resolving transparency strictly within the boundaries of a tile-owning thread block, the need for a global prefix scan and a global primitive sort is entirely eliminated. The workload scales linearly with resolution and geometry density, ensuring that the system is fundamentally resistant to the unpredictable global fragment populations that plague the current un-tiled architecture.

## **Paradigm V: Chunked Processing and Device Work Queues**

If transitioning to a fully tiled architecture requires too substantial an overhaul of the existing Cudapipe codebase, a middle-ground approach involves chunked processing combined with device-managed work queues. Instead of attempting to process an entire episode in a single monolithic pass, the episode is artificially segmented into smaller, mathematically bounded "chunks."  
A device work queue is instantiated in global memory. A scheduling kernel analyzes the episode and pushes chunk descriptors into the queue. Each chunk represents a subset of the primitive draws or a specific depth slice of the scene. The maximum possible number of fragments a chunk can generate is calculated analytically based on the primitive count and bounding box areas. The chunk size is throttled such that it mathematically cannot exceed the finite capacity of the fragment and quad arrays.  
A pool of worker thread blocks continuously polls the device work queue. When a block acquires a chunk, it processes it through the standard rasterize-scan-sort-shade-blend pipeline. Because the chunk is mathematically guaranteed to fit within the array capacities, the overflow flags and the subsequent CPU synchronization are rendered entirely obsolete. To preserve Vulkan's submission-order blending, the chunks must be dispatched and composited sequentially, or blended using subpass self-dependencies mimicking VK\_DEPENDENCY\_BY\_REGION\_BIT if spatial non-overlap can be guaranteed45. This paradigm trades optimal parallel occupancy for absolute memory safety, eliminating the catastrophic depth peeling fallback by ensuring the arrays are flushed and reused before they can ever overflow.

## **Paradigm VI: The Persistent Megakernel Approach**

The final, and potentially most radically efficient, architectural redesign considers the elimination of explicit kernel launch boundaries entirely. Currently, Cudapipe transitions between discrete kernels for rasterization, prefix scanning, sorting, shading, and compositing. Even when bound within a CUDA Graph, launching distinct kernels incurs state-saving overhead and mandates global memory synchronization between pipeline stages, as the prefix scan must wait for rasterization to complete across the entire GPU47.  
A persistent megakernel architecture fuses the entire episode pipeline into a single, monolithic CUDA kernel47. The kernel is launched exactly once per episode (or once per frame) with a grid size calibrated to exactly fill the GPU's available SMs. Once resident, the thread blocks never terminate; instead, they operate as a distributed software scheduler, dynamically pulling tasks from lock-free work queues residing in global memory29.  
The megakernel features distinct operational states: RASTERIZE, SCAN, SORT, and SHADE. As threads pull batches of primitives, they generate fragments and append them to a global warp-cooperative slab list (as explored in Paradigm II). To synchronize across the entire GPU without relinquishing control to the host CPU, the megakernel utilizes Cooperative Groups via the cudaLaunchCooperativeKernel API48 and grid-level synchronization barriers such as cudaGridDependencySynchronize8.  
When the fragment generation phase is complete, the thread blocks hit a global device barrier. They seamlessly transition into the SCAN and SORT states, processing the populated slab lists. Following another grid-wide barrier, they transition into the SHADE state, processing the ![][image1] quads and blending into the framebuffer.  
If the internal queues approach maximum capacity during the RASTERIZE phase, the megakernel can dynamically pause rasterization, execute a grid-wide synchronization, and immediately transition to SORT and SHADE to flush the buffers into the framebuffer. Once flushed, the blocks return to the RASTERIZE state to process the remainder of the episode. This internal state machine creates a self-regulating pipeline that naturally breathes with the geometric workload. Because the CPU is entirely excluded from the execution loop, launch overheads are driven to absolute zero, and partial commits are avoided by holding the intermediate results in the megakernel's internal data structures until the mathematically safe flush state is triggered.

## **Strategic Recommendations and Conclusions**

The synchronization bottleneck currently debilitating Cudapipe is an acute symptom of a broader architectural friction: the attempt to map unbounded, dynamically generated graphics data onto statically allocated compute paradigms. The CPU's involvement in evaluating overflow flags fundamentally violates the asynchronous execution model required for high-throughput GPU rendering.  
To achieve immediate relief with the lowest degree of pipeline refactoring, transitioning to **Autonomous Device-Side Control Flow via CUDA Conditional Graphs** is highly recommended. By encapsulating the existing optimal A-buffer pass and a newly ported CUDA depth-peeling fallback into a Switch conditional node (cudaGraphCondTypeSwitch), Cudapipe can entirely remove the host CPU from the episode rendering loop. The device natively evaluates the capacity counters via cudaGraphSetConditional and routes the execution gracefully, ensuring that Vulkan submission-order blending is preserved and incomplete data is safely discarded without incurring host-side latency.  
For a long-term, structurally profound redesign that scales with next-generation workloads, a **Tiled Sort-Middle Architecture** represents the zenith of software rasterization efficiency. By partitioning the framebuffer into spatial tiles, performing primitive binning, and isolating fragment generation and sorting to SM shared memory, the architecture inherently mitigates the threat of global array overflow. When combined with warp-cooperative slab lists to handle the exceptionally rare instances of localized tile overflow, the rasterizer gains true algorithmic elasticity. This approach not only aligns perfectly with the conceptual framework of Vulkan's Rasterization Order Attachment Access (ROAA) but also maximizes memory bandwidth, localizes non-commutative blending mathematics, and provides a scalable, device-autonomous foundation for Cudapipe's future evolution.
