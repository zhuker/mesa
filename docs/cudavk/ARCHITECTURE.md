# cudavk architecture

How the driver works, for someone who has to change it.

This document is the mechanism. It is not a decision log: why a mechanism has
the shape it has, what was tried instead, and what each step was worth are in
`history/VK_NATIVE_DECISIONS.md` and `history/PERF16_ITERATIONS.md`. Open
questions and known gaps are in `TODO.md`. What a frame costs and how that was
measured is in `PERFORMANCE.md`. How to build, run, test and profile is in
`WORKFLOW.md` and `TESTING.md`.

Every file path below is relative to the repository root unless it starts with
`history/` or `notes/`, which are beside this file.

---

## 1. What cudavk is

`src/cudavk/` is a Vulkan driver that rasterizes with CUDA compute kernels
instead of the GPU's fixed-function graphics pipeline. It builds one shared
object, `libvulkan_cudavk.so`, and one ICD manifest,
`cudavk_devenv_icd.x86_64.json`. An application reaches it through the ordinary
Vulkan loader.

Three facts shape everything else.

- **It is a native ICD on Mesa's common Vulkan runtime.** Instance, physical
  device, device, queue, command buffer, descriptor set layout, buffer, image
  and sync objects derive from the runtime's `vk_*` base structures, and the
  entrypoint table is generated by `vk_entrypoints_gen` with the `cpvk` prefix.
  There is no lavapipe and no Gallium below it. The Gallium-hosted driver this
  replaced has been removed; `GALLIUM_RETIREMENT.md` says what it could do and
  how to bring it back.
- **It advertises Vulkan 1.1** (`cpvk_device.c`, `VK_MAKE_VERSION(1, 1,
  VK_HEADER_VERSION)`), with one queue family that carries graphics, compute
  and transfer. 1.1 rather than 1.0 because at 1.0 the runtime does not wire
  the KHR alias entrypoints to its core implementations, so an application that
  enables `KHR_get_physical_device_properties2` jumps through a null pointer in
  the loader.
- **Everything the GPU does is a CUDA kernel.** The driver's own kernels are
  embedded as CUDA source from `src/cudavk/kernels/*.cu` and compiled by NVRTC
  when the device comes up; the application's shaders are compiled from SPIR-V
  to PTX by the driver itself. Every generated shader kernel is named `main`,
  which is why a name-only profiler summary is useless here — it sums the
  vertex and fragment stages into one row. See `WORKFLOW.md`.

### Source layout

| file | responsibility |
|---|---|
| `cpvk_target.c` | the ICD entry point, and nothing else |
| `cpvk_device.c` | instance, physical device, features, properties, the one queue family |
| `cpvk_device_memory.c` | logical device and CUDA context lifetime, queue submission, the three memory kinds, buffers, teardown |
| `cpvk_image.c` | the closed format table, tightly packed mip layout, images, views, texture descriptors, samplers |
| `cpvk_pipeline.c` | SPIR-V→NIR preparation, descriptor lowering, graphics/compute pipeline compilation, the in-process stage cache |
| `cpvk_cmd.c` | descriptors, command recording, dynamic rendering, draws, dispatches, copies, blits, resolves, events, queries |
| `cpvk_sync.c` | binary fences and semaphores, and timeline semaphores; one refcounted CUDA event per submit is the completion, on the device and on the host |
| `cpvk_texture_cache.c` | derived read-only CUDA arrays and texture objects for the hardware texture path |
| `cp_renderer.[ch]` | the renderer: batching, clipping, rasterization, A-buffer and peel paths, pass episodes, arenas, launches |
| `cp_kernels.[ch]`, `kernels/` | NVRTC compilation, the PTX disk cache, and the CUDA kernels themselves |
| `nir_to_ptx/` | the NIR→LLVM→NVPTX backend and the compiled shader binaries |
| `cp_shader_abi.h` | the one description of the shader argument block and the descriptor row |
| `cp_debug.[ch]` | the environment-switch registry |
| `tests/` | the native test programs and the whole measurement toolchain |

The split that matters is `cpvk_*` against `cp_*`. `cpvk_*` is Vulkan: objects,
lifetime, validation of what is legal. `cp_*` is the renderer: it knows about
draws, batches, kernels and CUDA, and takes no Vulkan type. Vulkan fixed-function
state is converted once into the renderer's own `cp_*` types (`cp_draw_types.h`,
`cp_draw_packet.h`). Nothing else crosses.

## 2. From `vkQueueSubmit` to pixels

### 2.1 Recording

A command buffer records a growable ordered array of `cpvk_op` values: begin and
end render, clear, query, copy, draw, dispatch, barrier, event order point.
Recording touches no CUDA.

Two rules make the array safe to grow and to import from a secondary buffer.

- **Operations refer to each other by index, never by pointer.** Each
  `vkCmdBeginRendering` owns an immutable `cp_render_scope`; draws carry a scope
  index. Array growth cannot invalidate an index.
- **A draw snapshots everything it depends on.** Framebuffer, viewport, scissor,
  vertex and index input, push constants and descriptor rows are copied into
  command-buffer-owned storage at record time. An application is allowed to
  rebind or rewrite the same descriptor set after recording a draw, so a
  recorded command must not point at a live set.

Descriptor snapshots go into a command-buffer arena that is split between
ordinary host staging and device-only storage. Retired arenas stay alive until
the command buffer is reset, because earlier draws still point into them.

When recording ends, `cpvk_plan_batches()` walks the finished array and fills
each scope's `planned_draws`, `planned_blended_draws` and `planned_tris`. That
is the record-time half of the plan: a sizing or path decision can read what the
pass will ask for before the first draw executes, instead of discovering it draw
by draw. `CUDAVK_PLAN_STATS` reports how often a merge was answered from the
plan and how often it had to be decided dynamically.

Secondary command buffers are appended to the primary's operation array by
memcpy. Their descriptor snapshots are imported into primary-owned arenas, draw
and dispatch addresses are remapped, and an inherited scope index resolves to
the primary's active scope.

### 2.2 Submission

`vkQueueSubmit` walks the recorded array in order and:

1. makes the renderer stream wait for each wait semaphore that carries a
   completion event, and host-waits the ones that do not;
2. publishes the bounded host mappings the sampler specializer and the hardware
   texture preflight read;
3. uploads dirty descriptor-snapshot arenas from host storage to device-only
   memory, once per recording rather than per draw;
4. issues draws, dispatches and transfers on the renderer's stream in recorded
   order;
5. flushes any pending renderer batch and finishes any open pass episode;
6. records a CUDA completion event, arms every sync it will signal with it, and
   returns **without draining the stream**.

A per-device completion worker waits on those events in queue order and only
then publishes the submission's signals. That is what makes fences and
semaphores track real GPU completion rather than host progress. Scratch and
upload generations are rewound only when all earlier submissions have retired.

Step 1 is a GPU dependency expressed as one, which is what a semaphore is. It
used to be `vk_sync_wait_many` on the application thread before a single
command was translated. The host wait is still there for the sync that has
nothing recorded into it — signalled from the host, or by a submit that has not
been issued yet — and `CUDAVK_NO_GPU_SEM_WAIT` puts everything back on it.
Step 6 also marks each signalled sync *pending*, which is what makes
`VK_SYNC_FEATURE_WAIT_PENDING` true and lets the runtime support
wait-before-signal on timeline semaphores over a driver that cannot (§2.2 of
`CUDA_INTEROP.md`).

Each recorded draw is resolved by `cpvk_prepare_draw()` into one complete
immutable `cp_draw_packet`: state, scope, call, index range, scissor, and the
already-uploaded push and per-stage UBO rows. `cp_draw_execute_batch()` is the
only draw executor. A direct draw is a batch of one.

### 2.3 The pipeline, per batch

```
  vertex stage      one thread per assembled vertex
                    fused build gathers its own attributes (§3.4);
                    otherwise cp_vertex_fetch runs first and packs them
        |
  clip              7 planes, in homogeneous space, before the divide;
                    fused with raster stage 1 by default
        |
  raster stage 1    one thread per triangle; small ones rasterized in place,
                    the rest pushed to the nontrivial queue
  raster stage 2    one warp per queued triangle; medium ones done here,
                    huge ones decomposed into (triangle, tile) pairs
  raster stage 3    one block per (triangle, tile) pair
        |
        +-- opaque draw ----> visibility buffer, then direct shading
        |
        +-- blended draw ---> A-buffer build, then A-buffer shading
```

The rasterizer writes a **visibility buffer**: one `uint64` per sample, packed
as `depth << 32 | ~triangle_id`, resolved by `atomicMin`. A minimum is
order-independent, and that single fact is what allows opaque draws to be
batched and opaque episodes to share one buffer (§4).

Every stage is bounded by the clip rectangle — framebuffer ∩ viewport, and the
scissor when the rasterizer state asks for it — computed on the host. A batch
whose draws disagree on the scissor carries one rectangle per draw and
`setup_triangle()` resolves the primitive to its draw.

Two rasterizer details are load-bearing and easy to break:

- **Coverage is watertight because `edge_function()` is exactly
  antisymmetric.** It is written as a cross product of the two vectors from the
  sample point, with explicit round-to-nearest intrinsics, so that swapping two
  vertices negates the result bit for bit. Contract those products into an FMA
  and two triangles sharing an edge can both reject a sample on it.
- **A point is one vertex wearing a square.** `POINT_LIST` arrives as one
  degenerate triangle per point; every stage resolves it with the same
  half-open box test, and `gl_PointCoord` is written by the interpolator from
  the pixel's position inside the square.

Clipping has a stable mode: input triangle *t* owns a fixed run of output slots
(`CP_CLIP_MAX_OUT` = 8, `CP_CLIP_PRIM_SHIFT` = 3), and the slots it does not
fill are retired as zero-area triangles. A batch's primitive index is then
monotone in submission order, which is what makes sorting blended fragments by
primitive index equal to sorting them by submission order. The stable path also
appends each live ID to a compact `active_ids` worklist, so the rasterizer
enumerates real work while queues and A-buffer records still carry the stable
ID. The older compacting path (`atomicAdd`) still runs where stability is not
needed.

### 2.4 The A-buffer

A blended draw cannot resolve to one fragment per pixel: every layer has to be
composited in submission order. The A-buffer does that in one build instead of
re-rasterizing the draw once per layer.

| step | what it does |
|---|---|
| count | a rasterization pass that counts depth-passing fragments per pixel, and — on the single-pass build — also appends one `pixel << 32 \| prim` record per fragment through one global cursor |
| scan | an exclusive prefix sum over the per-pixel counts, in blocks of `CP_ABUF_SCAN_BLOCK` (512), giving each pixel its run's base |
| fill | `cp_abuf_fill_recs` replays the appended records into the fragment array; without the records it rasterizes a second time |
| sort | each pixel's run sorted ascending by primitive index; short runs by one thread, longer ones in shared memory, runs above `CP_ABUF_SORT_MAX` (1024) by a slow global insertion sort |
| quad stream | per 2×2 block, the distinct primitives covering it and a 4-bit pixel mask each — this is what gets shaded, four lanes to a quad |
| shade | the fragment shader over the quad stream |
| composite | one thread per pixel with any fragment, walking its sorted run and blending each layer in order |

Two eligibility rules sit around the build. The fragment array is sized from
the first eligible draw's count with headroom (`CP_ABUF_HEADROOM`, 2x) and grown
between draws when a later count comes within `CP_ABUF_GROW_AT` (0.75) of
capacity, up to `CP_ABUF_MAX_GROWTHS` (8) times; a growth is applied by the
*next* draw, because the draw that asked for it is still reading the arrays a
resize would free. And a batch too small to pay for the build skips it:
`CUDAVK_ABUF_MIN_TRIS` is a triangle-count floor, known before anything is spent.
It defaults to 0 today, which is deliberate — the corrected bootstrap and the
zero threshold together are why the renderer does not return to an earlier
failure mode on Crossroads.

The composite loads and stores through the attachment's own encoding at every
layer. That is deliberate: the peel loop quantizes each layer before the next
one blends against it, and the claim this path is verified against is that it
reproduces the peel loop's image bit for bit.

The **peel loop** is the fallback and is still correct. It repeats the whole
draw, taking the earliest primitive each pixel has not composited yet, up to
`CP_BLEND_LAYERS` (256) passes. It runs for draws the A-buffer refuses:
multisampled, depth-writing, more than one colour attachment, or a colour format
with no encoding. `CUDAVK_NO_ABUFFER` puts everything back on it.

Fragment-shader side effects with no colour attachment also take the peel loop,
for the same reason and more literally: the visibility buffer would give such a
pass one fragment per pixel, and a shader that builds a per-pixel list needs all
of them.

### 2.5 Fragment execution

Fragments are shaded **four to a 2×2 quad**, so the sampler can take
screen-space derivatives by shuffling between lanes. A quad belongs to one
triangle, because differencing across two triangles produces a meaningless
derivative at every seam. Corners no triangle covers are shaded as helper lanes
and dropped later.

`cp_shader_binary` holds several independently linked executions of the same
shader (`enum cp_shader_exec_mode`, `nir_to_ptx/cp_nir_to_llvm.h`). Five of
them are fragment executions and one is the vertex fusion:

| mode | interpolation | texture reads |
|---|---|---|
| `CLASSIC` | separate `cp_fs_interpolate` launch | software sampler PTX |
| `FUSED` | in-shader, through the linked `cp_fs.cu` helper | software sampler PTX |
| `INLINE` | in-shader, from bitcode inlined in the same LLVM module | software sampler PTX |
| `HW_INLINE` | in-shader, same-LLVM | NVVM texture instructions on a CUDA texture object |
| `HW_FUSED` | in-shader, through the proven helper | NVVM texture instructions |
| `VS_FETCH` | — (vertex stage) | vertex attribute gather inlined into the shader |

They are separate `CUmodule`/`CUfunction` pairs, not one binary with a flag —
which is what makes selecting the classic one a real revert. When an in-shader
mode runs, the separate interpolation launch shrinks to `cp_fs_compact`: the
visibility scan and the atomic slot allocation, which the shader cannot do for
itself because it does not know its slot until it has one.

`cp_fs_writeback` closes the direct path. It drops helper lanes using the
coverage byte, honours the discard mask (recording which triangle discarded so
the next alpha-test pass can pick the one behind it), commits depth for the
samples the fragment won, blends, and stores through the attachment's encoding.
The destination is read only when the equation needs it.

Alpha-tested draws repeat the rasterize-and-shade sequence up to
`CP_DISCARD_LAYERS` (8) times, because visibility is resolved before shading and
a fragment that discards has already displaced the one behind it.

## 3. The shader path

### 3.1 SPIR-V to PTX

Mesa's common runtime translates SPIR-V to NIR. `cpvk_pipeline.c` then applies
the native preparation, and `nir_to_ptx/cp_nir_to_llvm.c` emits LLVM IR and runs
the NVPTX backend to PTX, which the CUDA driver JITs.

The preparation steps that are not optional:

- descriptor, image and texture lowering to the flat native descriptor ABI;
- `frag_coord` and point coordinates lowered to renderer-provided varyings;
- register-to-SSA cleanup immediately before the backend;
- fixed-point NIR optimization **only** for shaders containing loops — applying
  it to everything regresses straight-line shaders;
- vertex-input load hoisting with `nir_opt_move_to_top`;
- a resource-aware BLAKE3 cache key.

The cache key is resource-aware because SPIR-V alone is not enough: descriptor
layouts change the constant-buffer slots and flat offsets baked into the NIR.
Cache insertion does a second locked lookup after compilation so that concurrent
creators end up sharing one binary — pointer identity is itself part of the
batching contract (§4).

Each fragment shader also gets a register-cap trial: the driver compiles the
shader as the JIT built it and capped, times both on the application's own
draws, and keeps the faster unless the capped build is more than
`CUDAVK_TUNE_VETO` worse. The register *count* cannot be used to decide this,
because every sampler-linked shader has the sampler's allocation rather than its
own.

### 3.2 The ABI

`cp_shader_abi.h` is the single description of how a kernel reaches its
resources, with a static assertion for every number a CUDA kernel depends on.
Change the layout there and the build fails if the kernels disagree.

A kernel takes one argument: a pointer to an array of pointers.

- Slots 0..17 are fixed state — counts, input and output buffers, the
  fragment-coordinate array, draw parameters, the discard mask, the per-draw UBO
  table, the batch row array and mask, `gl_FrontFacing`, coverage, the fused
  interpolation block, the hardware texture table, the fused fetch block.
- From `CP_ARG_UBO_BASE` (18) there is one slot per constant buffer,
  `CP_MAX_CONST_BUFFERS` (16) of them. **A descriptor set occupies exactly one
  slot**, not one per binding, which ran out on a real pipeline layout. Slot
  `CPVK_UBO_PUSH_SLOT` (0) of that range is always push constants.
- A set's slot holds the address of a flat array of 64-byte descriptor rows. A
  binding is a byte offset computed at compile time by the descriptor lowering;
  an array element steps by one row.

Application binding numbers are sparse; the ABI's flat index is not. A layout
sorts its bindings once, assigns each a dense flat base, and NIR lowering, the
cache key, writes, copies and dynamic offsets all go through that one map.

Graphics adds one indirection the kernels do not have: when draws are merged the
slot array is per draw, and the shader selects its own row:

```
row  = batch_rows[thread_id & batch_mask]
base = ubo_table[row * CP_ARG_UBO_STRIDE + i]
```

All three slots are always filled, so there is no branch and no
batched/unbatched variant of the generated code. A single draw sets the table to
`&args[18]`, the mask to zero and a one-word row array holding zero, which makes
the expression compute exactly the `args[18 + i]` it used to.

Three descriptor-row offsets are read by CUDA code — the image base, the sampler
index, and the texture-info pointer — and are asserted against the header. Two
more fields are host-only cookies that no device code reads: the sampler cookie
and the 1-based stable image-view ID, which the hardware texture path uses to
find the derived CUDA array.

### 3.3 The same-LLVM bitcode inline mechanism

Two helpers are compiled from C to NVPTX bitcode at build time by the clang
whose major version matches Mesa's LLVM: `kernels/cp_fs_inline.c` (fragment
interpolation) and `kernels/cp_vs_inline.c` (the per-lane vertex fetch). The
driver never runs a compiler subprocess; the bitcode is embedded.

`link_and_inline_bitcode()` parses that bitcode into the **same `LLVMContext`**
as the generated shader, links it, marks the exported helpers internal, and runs
`always-inline` plus an SROA/mem2reg/GVN pipeline before the ordinary
optimization. The rules are strict on purpose:

- the helper module's target triple and data layout must match exactly;
- every named helper symbol must exist after the link;
- **no named helper symbol may survive the inlining.** A surviving symbol is a
  build failure, not a slower fallback, because a real device call is exactly
  what an earlier attempt measured at 20 → 108 registers.

After inlining there is no call, no callee frame to union a register allocation
with, and no ABI beyond the frozen struct layouts the helper asserts:
`cp_fs_inline.c` carries sentinel `_Static_assert`s on the size, alignment and
selected field offsets of `cp_fs_interp_args`, so an ABI drift fails the build
instead of being decoded wrongly at run time.

Both helpers use one idiom to stay in registers: loops bounded by a compile-time
maximum, skipping on the runtime count *inside* rather than exiting early, so
they unroll into stores at constant offsets and SROA can promote the caller's
array. A dynamically indexed alloca becomes local memory, which is the whole
thing this mechanism exists to avoid.

### 3.4 Fused vertex fetch, and its admission rules

`kernels/cp_vf_lane.h` is the per-lane fetch, shared by two compilers: NVRTC
compiles it as the body of the standalone `cp_vertex_fetch` kernel, and clang
compiles it to bitcode that is inlined into the generated vertex shader. Both
must produce bit-identical results, which is why the half-float decode stays
hand-written — the software decode is the definition.

The fused build is a second, independently linked execution. Admission compares
it against **the classic build of the same shader**, not against zero, because a
vertex shader may already carry a local depot for its own reasons
(`cp_vs_attach_fused_fetch()`):

| verdict | condition |
|---|---|
| `ADMITTED` | none of the below |
| `NO_BITCODE` | built without a matching clang |
| `DISABLED` | `CUDAVK_NO_FUSED_VFETCH` |
| `TOO_MANY_INPUTS` | more input slots than the fetch can gather |
| `COMPILE_FAILED` | codegen, link or JIT refused |
| `HELPER_SURVIVED` | a real call remained after inlining |
| `LOCAL_MEMORY` | more `.local` in the PTX than the classic build |
| `SPILL` | more spill bytes than the classic build |
| `OCCUPANCY` | fewer blocks per SM than the classic build |
| `FORCED_DECLINE` | `CUDAVK_VFETCH_DECLINE_NTH`, for the tests |

Verdicts are counted per shader and weighted by the launches each shader
actually receives, because a verdict counted per shader says nothing about the
frame. `CUDAVK_SHADER_STATS` prints them.

### 3.5 NVRTC kernels and the sampler modules

`cp_kernels.c` compiles `kernels/*.cu` with NVRTC at device init, keyed by the
exact source, the embedded header, all NVRTC options, the target SM and the
NVRTC version. When Mesa's disk cache is available the resulting PTX persists
there. This is a PTX cache, not an application `VkPipelineCache`: generated
application shader PTX and CUDA JIT products stay process-local.

Ordinary shaders link the small `cp_tex_sample` PTX. A NIR instruction that can
actually filter a 3D texture (`tex`, `txl`, `txb`) lazily compiles and links a
second module exposing `cp_tex_sample_3d`; `txf` and `txs` stay on the small
module. The split is load-bearing — putting both paths in every sampler module,
or branching inside one exported sampler, raised the register and JIT cost of
ordinary 2D shaders.

Sampler *specialization* bakes one sampler state into the kernel with defines. A
shader qualifies when every sampler handle it uses resolves to the same state.
The specializer recognizes an exact IR shape, so a lowering change can stop it
firing with no error at all; `CUDAVK_SPEC_STATS` is what makes that visible.

## 4. Batches, pass episodes and opaque episodes

Three structures group work. All three exist for the same reason: the fixed
costs of a draw — the visibility clear, the interpolation grid, the fragment
grid, the argument uploads — are sized to the framebuffer, not to the draw, and
a scene of small draws pays them over and over.

### 4.1 Batches

Consecutive draws that cannot produce different pixels by being merged are held
back and submitted as one. Eligibility is `struct cp_batch_key`, built by
`cp_batch_build_key()` from a zeroed struct and compared with `memcmp`. Anything
the builder does not copy is simply not a merge condition, which is what makes
"added state and forgot the key" a visible mistake rather than a silent one.

The key holds the two shader binary pointers, the framebuffer and the driver's
own per-pass buffers, primitive mode, index size, `start_instance`, the index
resource, the scissor, blend enable, the whole fixed-state block, the vertex
element layout counts and the binding counts.

What is deliberately **absent** is as important:

- the index range — a batch carries a table of ranges and the fetch
  binary-searches it, which is what lets different meshes out of one buffer
  merge;
- the vertex-buffer bindings — one row of resolved per-element base addresses
  per draw;
- the draw parameters — `gl_BaseVertex`, `gl_BaseInstance`, `gl_DrawID` resolve
  per draw through the parameter rows;
- the descriptor and push contents — every draw carries immutable per-draw
  rows, so requiring equal sets would split correct work without protecting
  anything.

Caps: `CUDAVK_BATCH_MAX` draws (default 128, and `CP_MAX_BATCH_DRAWS` is 128)
and `CP_MAX_BATCH_TRIS` (256 K) triangles, because the clipper's output buffer
scales with the batch and the arena has a hard limit.

`cp_batch_flush_why()` names the reason a batch ended;
`CUDAVK_DEBUG_BATCHDIFF` names the field two draws disagreed on.

At command-buffer end, the same record-time planner also removes draws from a
render scope whose only attachment result is immediately discarded. Admission
is intentionally narrow: the following scope covers the full same colour
subresource and begins with `LOAD_OP_DONT_CARE` or `CLEAR`; the old scope has no
depth attachment, resolve, query, event or unrelated operation; and neither
shader stage writes memory. Mesa's legacy-render-pass lowering may put a barrier
between the two scope markers, which does not make discarded colour contents
observable. The begin/end markers, barrier and old clear remain in the op list;
only provably dead draws are suppressed. `CUDAVK_DEBUG_RT` prints each admitted
scope as `dead-scope:`.

### 4.2 Pass episodes (blended)

Consecutive **blended** batches share one A-buffer build, one drain and one
composite. Each flushed blended batch becomes a *segment*: its vertex stage and
its A-buffer count rasterization run when it is appended, into per-pixel lists
shared by the whole episode, with its primitive IDs offset so that ascending
order is still submission order across segments. Everything after that — scan,
fill, sort, quad merge, the drain, per-segment shading, the composite — happens
once, at `cp_pass_finish()`.

Merging blended draws is legal only because the clipper's stable mode makes a
batch's primitive index monotone in submission order.

Bounds: `CP_PASS_MAX_SEGS` (64) segments, and a primitive-ID limit of
`CP_PRIM_ID_LIMIT` (2^30). Segments fan out across `CP_PASS_STREAMS` (8) side
streams, each with its own rasterizer queue set, and join at the phases that
read across segments. An episode refuses to open at all while the fragment array
has not been sized yet, while a growth is pending, or in verification, timing
and census modes, which read per-draw state the episode does not keep.

`cp_batch_flush_defer_why()` is the deferrable flush: the batch joins the
episode, but the episode stays open. Only four per-segment state changes may use
it — a draw whose key broke the batch, and the vertex-shader, fragment-shader
and vertex-element binds. Everything else goes through `cp_batch_flush_why()`,
which also finishes the episode, because everything else either observes
rendering or changes state the episode reads episode-wide.

### 4.3 Opaque episodes

Consecutive **opaque** batches share one visibility buffer, and their shading is
deferred to the end of the run. Admission (`cp_opaque_appendable()`) needs the
merge condition to be order-free plus a narrow framebuffer shape:

- `cp_batch_order_free()`: no blending, no discard, depth test and depth write
  both on, and a depth function of LESS, LEQUAL, GREATER or GEQUAL — so the
  `atomicMin` resolve is the answer whatever order the draws arrive in;
- the fragment shader writes no memory;
- one colour attachment, single-sampled, with a known encoding.

At `cp_opaque_finish()` the segments are grouped by shader pair, binding-row
width, primitive mode and draw count with identical fragment UBO rows, and each
group shades in one launch across several segments; a per-quad range table
resolves each quad's own vertex stream and slice table.

`CUDAVK_NO_PASS_EPISODE` and `CUDAVK_NO_OPAQUE_EPISODE` turn the two off.
`CUDAVK_FORCE_PASS_FALLBACK` makes every blended episode take the classic
re-execution fallback; the output must be identical, which is what makes it a
test.

## 5. The hardware texture cache

A software sampler reads an image through ordinary loads. The hardware texture
path lets the fragment shader issue NVVM texture instructions against a real
CUDA texture object instead. It is on by default; `CUDAVK_NO_TEXTURE_CACHE`
reverts it.

Three properties define it.

**The linear image stays authoritative.** The `VkImage`'s own allocation is
still the truth. The CUDA array is a *derived* copy, built from it, and nothing
reads back from the array into the image. An image qualifies only when it is
device-local, `VK_IMAGE_TILING_OPTIMAL`, single-sampled, not an alias, and its
format is in the closed table in `cpvk_texture_cache.c` (currently R8, R8G8,
R8G8B8A8, R16G16, R16G16F, R16G16B16A16F, A2B10G10R10, B10G11R11 and BC1/BC3;
the last three go through a conversion kernel into a surface).

**Freshness is an epoch.** Every write to a cached image bumps its
`content_epoch` and records a writer event on the writing stream. A resolve
compares the epoch the derived array was built at against the image's current
epoch; if they differ, the array is rebuilt, after a `cuStreamWaitEvent` on the
writer event so that the rebuild cannot overtake the write. The array is keyed
by (view cookie, sampler cookie), and the total is capped by
`CPVK_TEXTURE_CACHE_BUDGET` (384 MiB) with a purge path when it is exceeded.
That one is a compile-time `#define` in `cpvk_texture_cache.c`, not an
environment switch: every `CPVK_` *variable* name is retired.

**Admission is transactional and per launch, not per texture read.** Before a
fragment launch, `cp_texture_cache_available()` walks every static sampled site
in the shader (`cp_hw_tex_site`, up to `CP_MAX_HW_TEX_SITES` = 64) for every
per-draw row, reads the image and sampler cookies out of the descriptor rows
through the published host mappings, and resolves them all. **If any one of them
declines, the whole launch falls back to the software sampler.** There is no
mixed launch. The resolved `CUtexObject` values are uploaded as one immutable
table at `CP_ARG_SLOT_HW_TEX_TABLE`, and the cache is pinned for the launch's
duration.

A shader that indexes its samplers dynamically has no static site list, so it
never takes this path. Failures are classified into disposable refusals
(fall back, count it) and fatal ones (latch device loss), and there is a fault
injection switch for each stage — see the `CUDAVK_TEXTURE_CACHE_FAIL_*` flags
and the `cpvk_texture_cache_*_gate.py` tests.

`CUDAVK_TEXTURE_CACHE_STATS` reports hits, the two fallback classes and the
register/occupancy distribution per mode.

## 6. Memory

### 6.1 Vulkan memory

One device-local heap and three memory types (`cpvk_device_memory.c`):

| type | Vulkan properties | CUDA backing |
|---:|---|---|
| 0 | `DEVICE_LOCAL` | `cuMemAlloc`, never host-mapped |
| 1 | `HOST_VISIBLE + HOST_COHERENT + HOST_CACHED` | `cuMemAllocManaged` |
| 2 | type 1 plus `DEVICE_LOCAL` | `cuMemAllocManaged` |

The two host-visible types share an implementation but keep distinct property
requirements, because a captured application asks for both. They are managed
rather than pinned so that a frequently GPU-read page — a UBO, an SSBO — can
migrate to the device instead of being read over PCIe every time.

Images use one allocation with an explicit offset, row stride and level size per
mip, tightly packed. For a 3D image, `img_stride` and CUDA's `depthPitch` mean
one z slice, not a whole level.

### 6.2 The renderer's arenas

Four separate pools, and the distinction between them is the point.

- **Scratch (managed), `cp_scratch_alloc()`.** A bump allocator over managed
  memory, for buffers the host and the device both touch. It grows by doubling
  and refuses past `CP_SCRATCH_MAX_BYTES` (8 GiB) — managed memory is backed by
  system RAM, so a runaway allocation loop takes the machine down with the OOM
  killer instead of failing.
- **Device scratch (`dscratch`), `cp_scratch_alloc_device()`.** The same bump
  allocator over `cuMemAlloc` memory, and where everything a draw shades through
  belongs: vertex shader output, interpolated fragment inputs, shaded results.
  Those are written by one kernel and read by the next and never touched by the
  host — but out of managed memory they still cost as if they were, because the
  arena's bump pointer climbs and the first kernel to write a page pays the
  migration. It returns a `CUdeviceptr`, so a caller who dereferences it does
  not compile.
- **The upload ring.** A 256 MB device-only arena plus 8 MB of pinned host
  staging. `cp_upload_begin()` reserves 256-byte-aligned room and returns *both*
  ends — the device address the block will land at and the staging bytes to
  write into — so a block can refer to itself. That is required: the vertex
  argument array holds a device pointer to the per-draw uniform table sitting
  behind it in the same block. Pinned rather than malloc'd because only a pinned
  source makes `cuMemcpyHtoDAsync` genuinely asynchronous.
- **Framebuffer-sized buffers** (visibility, depth, reject, resolved,
  `peel_next`) are grow-only, kept at the largest size seen. An application
  renders more than one size, and an equality test against the bound size
  reallocated all five in both directions several times a frame.

### 6.3 The coalesced flush and the counter block

Two mechanisms remove small device operations from the hot path.

**Upload coalescing.** `cp_upload_end()` does not copy. It records that the
staging bytes below the watermark are owed to the device. One copy per flush
point sends the whole span. Every `cp_launch()` is a flush point, and the copy
goes on the same stream as the kernel, so same-stream ordering puts it first. An
open reservation holds the watermark back, so half-written bytes are never sent.
The span is exact because the device and host offsets advance by the same size
from bases a constant apart. `CUDAVK_NO_UPLOAD_COALESCE` restores one copy per
block.

**The counter block.** Every scalar counter the A-buffer owns lives in one
allocation, in the order the readback wants: scan total, fill overflow, long
runs, quad total, quad overflow, `clist_count`, then the per-segment quad counts
and the record cursor. One `cuMemsetD32` clears all of them and one copy reads
them back. Per-pixel arrays stay out of it — a counter whose size depends on the
framebuffer does not belong there. `CUDAVK_NO_COUNTER_BLOCK` restores the
per-counter clears.

**Flush generations.** `cp_flush()` no longer drains the device. The scratch and
upload arenas are split into `CP_FLUSH_GENS` (8) generations; the flush records
a retire event behind the generation it leaves and rewinds into the one whose
event — from seven flushes ago — it waits on, which is almost always already
signalled. `CUDAVK_FLUSH_DRAIN` restores the draining flush and a single
generation.

## 7. The flag registry

The driver has 97 environment switches (`src/cudavk/FLAGS.md`, generated) and
reads **none** of them with `getenv` on a hot path. They are declared in one
array in `cp_debug.c`, parsed once by `cp_debug_init()` at physical-device
enumeration into a read-only `struct cp_debug`, and read as
`cp_debug->field`. `apply_couplings()` then derives the flags that depend on
each other — `CUDAVK_NO_TEXTURE_CACHE` sets `cp_debug->texture_cache` there, so
no use site changed when that path was made the default.

A new switch goes in that array. The array is the single source of truth for the
name, the parse, the default and the one-line meaning, which is what makes
`CUDAVK_HELP=1` and the generated `FLAGS.md` correct by construction.
`src/cudavk/tests/cp_debug_doc.py --check` fails if the two have drifted. Run it
after touching the array.

Two boolean kinds exist and both are load-bearing. **Presence** flags are set by
the variable existing at all, so `CUDAVK_DEBUG_DRAW=0` turns tracing *on*.
**Value** flags read the value, so `=0` turns them off. That is not a design; it
is what they grew into, and it is preserved because someone's script sets one of
these to 0 today. `CUDAVK_HELP=1` says which kind each one is.

The registry is the driver's debugging surface, and it is organized as one:
tracing and per-subsystem statistics (`CUDAVK_PLAN_STATS`, `CUDAVK_SPEC_STATS`,
`CUDAVK_UPLOAD_STATS`, `CUDAVK_SHADER_STATS`, `CUDAVK_TEXTURE_CACHE_STATS`,
`CUDAVK_NVTX`); **a revert for every optimization that is on by default**, which
is the pattern to follow when adding one, because it is what makes an A/B
possible at all; fault injection for paths that are otherwise unreachable, such
as the texture cache's allocation, conversion and upload failures; and negative
controls for the checks themselves — `CUDAVK_ABUF_FUSE_BREAK` makes the A-buffer
fusion's equivalence gate fail on purpose.

Nothing in the driver reads the environment outside the registry, and that is
checked rather than asked for: `tests/cp_no_getenv.py` fails on any `getenv` in
driver sources, allowing only `cp_debug.c` itself and the separate programs
under `tests/` and `samples/`. It also catches `debug_get_bool_option` and its
relatives, which are a `getenv` with a default folded in and hide a switch from
`CUDAVK_HELP=1` in exactly the same way.

There used to be a second family here. Nineteen `CPVK_*` switches were read
with `getenv` across `cp_renderer.c`, `cpvk_cmd.c` and `cpvk_pipeline.c`,
including four on-by-default reverts of the kind this section tells you to add
— invisible to `FLAGS.md`, unannounced by `CUDAVK_HELP=1`, and one of them,
`CPVK_NO_BATCH`, a duplicate sitting three lines from the registry field that
already did the same thing. They are now registry entries under `CUDAVK_`
names. Their old names live in a retired table in `cp_debug.c` that names the
replacement on stderr, so a script or a shell still carrying one is told, not
ignored.

## 8. Invariants a change must not break

Each of these was paid for. The reason is one line; the long version is in
`history/VK_NATIVE_DECISIONS.md`.

**Recording and submission**

1. A recorded command never points at live application state. *An application
   rebinds and rewrites descriptor sets after recording a draw.*
2. Operations refer to each other by index, not by pointer. *The operation array
   grows, and secondary buffers are appended into it.*
3. `vkQueueSubmit` returns without draining, and signals are published by the
   completion worker. *Fences and semaphores must track GPU completion, not host
   progress.*
4. Arena generations are rewound only when the submissions using them have
   retired. *Otherwise the next submit hands out addresses a running kernel is
   still reading.*
5. `batch_uploads_live` prevents `cp_scratch_reset()` from rewinding the upload
   arena under a staged batch's rows. *A reclaim there gave the batch's own
   slice table the addresses its push blocks were sitting at.*

**Ordering and correctness**

6. Anything that observes rendering — a readback, a clear, a blit, a dispatch, a
   flush — calls `cp_batch_flush_why()` first. *A pending batch has not run yet.*
7. Only the four per-segment state changes may use the deferring flush. *Every
   other state change either observes rendering or changes state the episode
   reads episode-wide.*
8. Blended merging requires the clipper's stable mode. *Sorting by primitive
   index is only sorting by submission order while the clipper keeps IDs
   monotone.*
9. Opaque merging requires `cp_batch_order_free()` to hold. *Merging is safe
   only because `atomicMin` is order-independent.*
10. A fragment shader's stores and atomics must be suppressed for helper lanes.
    *Quads shade corners no triangle covers, and Vulkan says their side effects
    do not happen.*
11. `edge_function()` stays exactly antisymmetric, with explicit rounding
    intrinsics. *Contraction into an FMA puts a hole along every shared edge.*
12. An unsupported format or feature is refused, not advertised and clamped
    later. *An unimplemented operation that returns zero destroys everything
    downstream; a `textureSize` of zero made a blur kernel compute `1/0`.*

**The shader ABI and compilation**

13. Every kernel-visible ABI number lives in `cp_shader_abi.h` or
    `kernels/cp_rast_types.h`, with a static assertion. *The layout used to be
    described in four places and asserted in none.*
14. A descriptor set occupies one constant-buffer slot, not one per binding.
    *One slot per binding ran out on a real pipeline layout.*
15. Every fixed argument slot is used by exactly one thing, and all of them sit
    below `CP_ARG_UBO_BASE`. *A collision hands a gather a UBO pointer.*
16. No inlined helper symbol may survive `always-inline`. *A surviving device
    call is what took a 20-register vertex shader to 108.*
17. Shader binaries are shared by content hash, and the batcher compares
    pointers. *Compiling the same SPIR-V twice makes every draw between the two
    pipelines refuse to merge.*
18. Adding an execution mode means auditing every predicate over the mode enum.
    *A mode added beside the others is not automatically excluded from the tests
    that were written for a smaller set.*

**Flags and evidence**

19. A new switch goes in the `cp_debug.c` registry, never a new `getenv`.
    *`CUDAVK_HELP=1` and `FLAGS.md` are generated from the array, and the flags
    are how the next person finds anything.*
20. An optimization that is on by default ships with a revert switch. *Without
    one there is no A/B, and the first bisect step is a rebuild.*
21. A new default path keeps the old one runnable and equivalent. *The peel
    loop, the classic fragment execution and the unfused clip are all still
    exercised, and each has caught a regression in the path that replaced it.*

## 9. What is not implemented

The driver advertises Vulkan 1.1, and that advertisement is **not
conformant**. Four limits are honestly below their core minimum because the
matching functionality does not exist: `maxColorAttachments` and
`maxFragmentOutputAttachments` are 1, `maxFramebufferLayers` is 1, and
`maxDescriptorSetInputAttachments` is 0. Closing that means implementing
multiple colour attachments, layered rendering and input attachments — not
raising the numbers. Running the native suite under
`VK_LAYER_KHRONOS_validation` is the way to see what is left; see
`history/VK_NATIVE_DECISIONS.md`, "Known issues and deliberate limits".

The shape of the rest, in one list. `TODO.md` is authoritative and has the
current state of each; `history/HANDOFF.md` "Known gaps" has the long form with
the evidence behind it.

| area | what is missing |
|---|---|
| attachments | one colour attachment, no layered rendering, no input attachments — the four limits above |
| enumeration | only CUDA device 0 is exposed, even when CUDA reports more |
| rasterization | no line primitives; points and multisampling both work |
| multisampling | sample shading is per fragment only, so `sampleShadingEnable` and `minSampleShading` are ignored. Stencil, multiview, layered draws and depth resolve are rejected rather than approximated |
| blending | `VK_BLEND_FACTOR_CONSTANT_COLOR` and `CONSTANT_ALPHA` are enumerated and silently return 1.0 |
| vertex input | attribute divisors above one are unreachable — the pipeline ignores `VkPipelineVertexInputDivisorStateCreateInfoEXT`, though the fetch itself handles an arbitrary divisor |
| formats | the blit family is `R8G8B8A8_UNORM` and `B8G8R8A8_UNORM`; the copy executor has no host fallback. `R8G8B8A8_UINT` is the only integer colour format and is renderable and copyable only: there is no `CP_TEXEL_*` decode for it, so it cannot be sampled or blitted, and it is single sample because `cp_resolve_samples` averages and an integer resolve may only take sample zero |
| WSI | `EXT_headless_surface` only, no platform window-system extension |
| synchronisation | no external semaphore of any kind, and none is possible: CUDA 12.8 can import a semaphore but has no call that creates or exports one. Timeline semaphores are implemented, and their wait-before-signal is the runtime's ASSISTED mode rather than a native `WAIT_BEFORE_SIGNAL` |
| determinism | the compacting clipper path does not promise stable primitive order, so unblended draws can break a depth tie differently run to run |
| precision | raster stages 2 and 3 interpolate depth with separately written arithmetic, so a one-ulp difference flips a tie at the boundary; `fexp2`, `flog2` and lowered `fpow` use the NVVM approximate intrinsics |
| safety | `bindless_image_store` has no bounds check |
| combinations | peeling and the alpha-test retry loop both want the same multi-pass machinery and do not combine |

One difference is recorded as closed rather than as a defect: anisotropic
filtering under-blurs relative to NVIDIA's, which Vulkan leaves
implementation-defined and on which llvmpipe differs in the same direction. Do
not reopen it on a pixel count alone — the gap entry says what is already known.
`texture3d` drifting over an animation is a real undiagnosed defect and is in
`TODO.md`.
