# Targeting sm_120: what it would buy, and what is actually leaking

The driver compiles its NIR-derived shaders for `sm_86` with PTX ISA 7.5, not
for the RTX 5090's `sm_120`. This is the record of asking whether raising that
is worth doing.

**It is not. Nothing in the sm_86 → sm_120 delta has a user on the path LLVM
gates.** The features that would matter are already reachable today from the
`.cu` side, which never went through LLVM. Meanwhile the shader path is
emitting IEEE correctly-rounded divide and square root where an approximation
is allowed, and that costs **half the instructions and 22 registers** in
pbribl's fragment shader — on the LLVM and architecture the tree already has.

---

## Why the cap exists

`compile_module_to_ptx()` in `nir_to_ptx/cp_nir_to_llvm.c` builds its target
machine with cpu `sm_86` and features `+ptx75`, capped by `CP_MAX_PTX_SM` at
line 22. Every generated shader therefore opens:

```
.version 7.5
.target sm_86
```

This is not conservatism about a working alternative. LLVM 18's NVPTX backend
tops out at `sm_90a` and `ptx83`, and `.version` and `.target` are coupled — an
ISA version only knows the architectures that existed when it shipped:

```
$ llc -march=nvptx64 -mcpu=sm_120 -mattr=+ptx83 t.ll -o a.ptx
'sm_120' is not a recognized processor for this target (ignoring processor)
$ ptxas -arch=sm_120 a.ptx
ptxas error: PTX .version 8.3 does not support .target sm_120
```

sm_120 needs PTX ISA 8.7 (CUDA 12.8). **LLVM 18 cannot emit loadable sm_120 PTX
at any setting.** Only LLVM 20 or newer can, and `llvm-20-dev` is available in
apt here (`1:20.1.2-0ubuntu1~24.04.3`) but has never been installed. Nothing in
the tree pins 18 — meson's `llvm-config` fallback list finds
`/usr/bin/llvm-config-18`, the only LLVM on the machine, and the build's
requirement is `>= 8.0.0` (`meson.build:1985`; the `>= 18.0.0` branch above it
is radeonsi's).

Note the failure mode is nastier than a clean error. `llc` warns on stderr but
still writes `.target sm_120` into the header, so the module looks correct and
dies at load. That is what the comment at line 2125 is guarding against.

**Raising the cap would not remove the JIT.** The driver emits PTX text and
hands it to `cuLinkAddData(CU_JIT_INPUT_PTX, …)` or `cuModuleLoadData`
(`cp_nir_to_llvm.c:2300`, `:2438`), so ptxas runs at load time whatever
architecture the PTX names. ptxas also compiles for the *context's* device
regardless, so register allocation, scheduling and SASS selection already
target sm_120. PTX forward compatibility is what makes this legal, and it
holds:

```
$ ptxas -arch=sm_120 b.ptx     # b.ptx is .version 7.5 / .target sm_86
(no error)
```

What the cap costs is only PTX-level expressiveness — instructions LLVM would
be allowed to spell at a higher target. If load-time JIT cost is ever the
concern, the lever is a cubin cache, not the LLVM version.

---

## The sm_120 features, and who could already use them

The gate applies only to LLVM-generated shaders. The `.cu` kernels
(`kernels/cp_rasterize.cu`, `cp_fs.cu`, `cp_sampler.cu`, `cp_clear.cu`,
`cp_vertex_fetch.cu`) go through NVRTC 12.8 at `--gpu-architecture=compute_120`
(`cp_kernels.c:61`), so the whole sm_120 ISA is open to them now. Checked
against ptxas 12.8:

| instruction | `-arch=sm_120` | reachable from |
|---|---|---|
| `griddepcontrol` (programmatic dependent launch) | OK | `.cu`, today |
| `barrier.cluster` (thread block clusters, DSMEM) | OK | `.cu`, today |
| `elect.sync` | OK | `.cu`, today |
| `redux.sync` | OK | sm_80+, so even LLVM 18 at sm_86 |

`griddepcontrol` is the one worth arguing for — this driver issues thousands of
launches per frame, and letting a dependent kernel run its prologue before the
previous one drains is exactly the shape of that problem. It needs no LLVM
change at all. Same for clusters and distributed shared memory if tile binning
ever wants to share across CTAs.

What is left in the sm_86 → sm_120 delta for the *shader* path is tensor cores
and `tcgen05`, fp8/fp4, TMA and `cp.async.bulk`. A fragment shader here is
scalar f32 ALU, global loads, and a call into the linked sampler. None of it
has a user, and those instructions are intrinsic-only in the NVPTX backend, so
LLVM would not emit them from `cp_nir_to_llvm.c`'s generic IR even at sm_120.

## What is actually leaking

`CUDAPIPE_DUMP_PTX=1` on pbribl, opcode histogram of the largest fragment
shader dump:

```
   574  mul.rn.f32        117  div.rn.f32         0  fma.rn.f32
   380  add.rn.f32         22  sqrt.rn.f32        0  div.approx / div.full
                            3  rcp.rn             0  sqrt.approx / rcp.approx
```

Every divide and square root is the IEEE correctly-rounded form, which on
NVPTX is a long software sequence. The cause is that they are built with no
fast-math flags:

- `nir_op_fdiv` → bare `LLVMBuildFDiv` (`cp_nir_to_llvm.c:1486`)
- `nir_op_frcp` → bare `LLVMBuildFDiv(1.0, x)` (`:1411`)
- `nir_op_fsqrt` → bare `llvm.sqrt` (`:1399`)

`nir_op_frsq` already does the right thing — `llvm.nvvm.rsqrt.approx.f` at
`:1402`. The precedent is in the file; div, rcp and sqrt just never followed it.

### The measurement

The real dumped shader PTX, assembled for sm_120 with `ptxas -O3 -c`, SASS
instructions counted with `nvdisasm -c`:

| variant | SASS | registers |
|---|---|---|
| **as emitted** (`div.rn` + `sqrt.rn`) | **2168** | **64** |
| `div.full` | 1248 | 64 |
| `div.full` + `sqrt.approx` | 1152 | 42 |
| `div.approx` + `sqrt.approx` | 1040 | 42 |
| `div.approx` + `sqrt.approx` + contraction | 944 | 42 |

Half the instructions, and 64 → 42 registers. The register drop is worth as
much as the instruction count: `link_shader_module()` carries
`CUDAPIPE_MAX_REGISTERS` precisely because Sponza's fragment shader came out at
195 registers and capped theoretical occupancy at 16.7%, with ncu measuring
8.8% achieved.

**Do not chase FMA contraction.** ptxas already emits 377 FFMA despite the
explicit `.rn` forms, and allowing contraction on top only moves 2168 → 2080,
4%. The entire win is div and sqrt.

### Reproducing it

```bash
S=/tmp/ptx
cd ~/git/Vulkan
SAMPLES=pbribl VALIDATION=0 OUT=$S/out CUDAPIPE_DUMP_PTX=1 \
  VK_ICD_FILENAMES=~/mesa/build-cudapipe/src/gallium/targets/cudapipe/cudapipe_devenv_icd.x86_64.json \
  ./run_offscreen.sh
# the dumps land in $S/out/_logs/pbribl.log, 11 of them; take the one with the
# most div.rn.f32, and trim to the last closing brace at column 0 — the log
# continues past the PTX and ptxas stops at the first non-PTX line.
sed -e 's/div\.rn\.f32/div.full.f32/g' -e 's/sqrt\.rn\.f32/sqrt.approx.f32/g' \
    shader.ptx > shader_apx.ptx
for f in shader.ptx shader_apx.ptx; do
  ptxas -arch=sm_120 -O3 -c -v $f -o c.cubin
  nvdisasm -c c.cubin | grep -cE '^\s+/\*[0-9a-f]{4}\*/'
done
```

`-c` matters: the shader calls into the sampler, so it will not assemble
non-relocatable.

## What this does not establish

- **It is a static instruction count on one shader, not frame time.** Fewer
  instructions is not less time. `tests/cp_gpu_busy.sh` first — a shader-side
  win is invisible on a host-bound sample — then the benchmark sweep.
- **It is a precision change and has to be checked as one.** The gallery
  against the stored NVIDIA reference, and dEQP. This tree has a history of
  precision changes moving images: the anisotropic filtering difference, and
  the `lower_sincos` decision that the instancing sample's asteroids forced.
- `div.full.f32` (full range, ~2 ULP) is the conservative choice and already
  takes 2168 → 1248 on its own. `div.approx.f32` is faster but flushes
  denormals and has input range limits; it should have to earn the extra 200
  instructions against the reference images.

## If the LLVM 20 question comes back

Two caps are in play and they are independent: `CP_MAX_PTX_SM` at 86, and
`+ptx75` at line 2152. Both sit below LLVM 18's own ceiling of `sm_90a` /
`ptx83`. The cheap experiment is to raise the pair to `sm_90` / `+ptx83` on the
LLVM already installed and diff the emitted PTX. If nothing moves there, sm_120
via LLVM 20 will not pay for the toolchain churn either.

# Tried, measured, reverted — and the reason generalises

The div/sqrt change above was implemented and swept. **The instruction win is
real and larger than predicted. It buys nothing, and it costs precision.**

| shader | SASS before → after | regs |
|---|---|---|
| pbribl largest FS | **2168 → 1088** (−49.8%) | 64 → 42 |
| gltfscenerendering FS | **648 → 288** (−55.6%) | 66 → 56 |
| gltfscenerendering VS (no divides, control) | 408 → 408 | 56 → 56 |

Sweep: **47.58 → 47.55 ms, −0.1%.** `gltfscenerendering` 13.93 → 13.86, which
is inside the run-to-run spread. And that sample is the one this should have
shown on: 93% GPU busy, kernel-bound, with the fragment shader at 51% of the
frame.

**Why it buys nothing, and this is the part worth carrying.** Traced over 60
frames, the fragment kernel's median launch goes **136.88 → 136.46 µs, −0.3%,
after losing half its instructions.** `tests/TESTING.md`'s device-counter table
has this sample issuing on **3% of cycles**. The kernels are *stalled*, not
instruction-limited, so deleting instructions changes nothing — the shader
spends its time waiting on memory, and `ncu` agrees: `long_scoreboard` and
`wait` dominate, SM throughput under 8%.

**That generalises to Phase 0.** §0.1 (specialize on sample count), §0.2 (fold
the half-pixel offset), §0.3 (fast division) and §0.6 (cheap early-outs) are all
constant-factor instruction reductions in kernels the same counters put at 1-6%
issue. This is the first direct test of that class of change on this driver, on
a shader where the reduction was 50%, and the frame did not move. Measure the
issue rate before taking any of them.

**And it costs a real precision change.** `texturecubemap` is deterministic
against itself — floor exactly zero — and the change puts 1-5 pixels per frame
over tolerance 8 on **32 of 60 frames, max per-channel delta 175**: isolated
pixels in high-gradient regions where the reflection lands on a different texel
or cube face. No verdict moved and it is +0.007% against NVIDIA over the
animation, but a zero floor is a zero floor. `pbribl` is the honest PBR reading:
2098 pixels differ, none by more than 3/255.

`div.approx` was not tested. On this evidence there is nothing for it to win.

## One correction to the analysis above

The section "What is actually leaking" says the IEEE forms come out "because
they are built with no fast-math flags". **Adding fast-math flags does nothing.**
LLVM 18's NVPTX selector reads only the global `-nvptx-prec-divf32` option, so
`fdiv arcp afn float` still emits `div.rn.f32` — verified with `llc-18` — and
there is no `llvm.nvvm.div.full` intrinsic. Inline asm is the only route that
does not set a process-wide `cl::opt`, which would also move llvmpipe's gallivm
in the same process.

Reproduction of the revert-able change, should anyone want to re-measure:
`nir_op_fdiv` and `nir_op_frcp` to inline `div.full.f32`, `nir_op_fsqrt` to
`llvm.nvvm.sqrt.approx.f`, all guarded on `bit_size == 32 && num_comp == 1`.
Iteration `build/iter/fastdiv`, profiles `build/prof/{fdapx,fdprec}`.
